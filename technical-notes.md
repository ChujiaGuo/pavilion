## Recommended Stack

| Layer | Choice | Rationale |
|---|---|---|
| Language | TypeScript (full stack) | Shared types between frontend and backend; catches domain model errors at compile time |
| Monorepo | npm workspaces (or Turborepo) | `/client` + `/server` + shared `/packages/types` in one repo |
| Frontend | Next.js | React-based, SSR/SSG, good mobile-responsive support, large ecosystem |
| Backend | Node.js + Hono (separate service) | TypeScript-first, significantly faster than Express, minimal bundle (~14kb), clean modern API — chosen over Express which has weak native TS support and slow project velocity |

| Messaging | Stream Chat | Pre-built React components, handles realtime/push/storage |

| Hosting | Render | Low ops overhead, easy to start; free tier suits low traffic while pre-revenue |

## Supabase vs Firebase

Chose **Supabase (PostgreSQL)** over Firebase (Firestore) for the following reasons:

- **Relational data model** — users → sessions → ratings → venues are deeply relational. SQL joins are natural; Firestore requires manual denormalization and multiple round trips for the same queries.
- **Rating calculations** — weighted averages, session history, anomaly detection, distribution calibration all map cleanly to SQL. Firestore cannot do this without significant workarounds.
- **Geospatial search** — PostGIS extension gives native "venues within X miles" queries. Firebase has no equivalent. (This is the stack-choice rationale, not a status report: the schema is ready — `venues.location geography(Point,4326)` with a GIST index — but `venue.service.ts` doesn't query it yet; `listVenues` only filters by city/type/drop-in availability. Not yet implemented.)
- **Row Level Security (RLS)** — "default private" profile access enforced at the DB layer, not just application code. Harder to accidentally expose data. (Stack-choice rationale, not a status report: no migration enables RLS or defines a policy yet, and adding one wouldn't currently change anything — `service_role` has Postgres's `BYPASSRLS` attribute unconditionally, so it ignores RLS policies regardless of whether they exist. All current authorization, including admin checks, is enforced in service-layer code instead. See "Admin access check" below. The actual risk this stack carries is the service-role key itself leaking — env-var-only, gitignored, never sent to the client — since a leak grants unrestricted DB access that no RLS policy could have stopped. RLS would earn its keep as defense-in-depth only if a future feature has the client talk to Supabase directly with a user JWT, e.g. Realtime chat subscriptions — that path bypasses the Hono server's checks entirely, so it'd need real policies, not just service-layer logic.)
- **Marketplace readiness** — inventory, orders, commissions, and transactions are relational by nature. Adding the marketplace to Postgres is natural; retrofitting Firestore is painful.
- **Open source / no vendor lock-in** — can self-host if pricing becomes an issue. Firebase is Google-only.
- **Predictable pricing** — Supabase bills by compute/storage; Firebase bills per read/write (can spike unpredictably at scale).

Firebase would win on offline-first mobile support — relevant for native apps, not for web-first v1.

## Architecture

**Pattern: Modular Monolith for v1**

True microservices from day one add significant operational overhead (API gateway, service discovery, inter-service communication, container orchestration, distributed tracing) before the product is validated. A modular monolith deploys as one unit but enforces strict domain boundaries internally — when the marketplace is ready to be built, it extracts cleanly as a true service.

**Domain boundaries (no cross-domain imports):**

| Domain | Responsibility |
|---|---|
| `user` | Auth, profiles, privacy settings, verification |
| `venue` | Listings, geospatial search, discovery |
| `session` | Creation, RSVPs, scheduling. *(Payments and shuttle cost auto-calc are deferred — see brainstorm.md Future Features Roadmap.)* |
| `rating` | Score calculation, history, locks, anomaly detection |
| `messaging` | Thin wrapper over Stream Chat (session-scoped group chat) |
| `marketplace` | Stub only, fully deferred — don't implement or reference from other domains |

This is the single canonical copy of this table — `README.md` and `CLAUDE.md` reference it rather than duplicating it.

- **Modular from the start** — marketplace is deferred but must be addable without reworking core. Keep shop/inventory/payment concerns as a clearly bounded domain stub, even if the code doesn't exist yet.
- **No booking transactions in v1** — the app is a coordination layer. No payment flows for venue bookings or for paid (organizer-hosted) sessions; those are deferred to v2 (see brainstorm.md Future Features Roadmap). Organizers collect payment externally.

## Auth

**Email/password — implemented.** Signup/login are client-only pages (`src/client/src/app/signup/`, `.../login/`) that call Supabase Auth directly via `@supabase/ssr`'s `createBrowserClient` (`src/client/src/lib/supabase/client.ts`) — there's no `/api/auth` endpoint on the Hono server. `signUp` passes `display_name` in `options.data`, which the `handle_new_user` trigger (`supabase/migrations/20260629000000_initial_schema.sql`) picks up when it auto-creates the `profiles` row; none of the form's other fields (`city` — required; `firstName`/`lastName` — optional, per design-system.md's UX Principles) are part of that trigger, so the client immediately follows up with a single `PATCH /api/users/:id` (`src/client/src/lib/api.ts`'s `apiPatch`, bearer token from the just-created session) that always sets `city` and conditionally includes `firstName`/`lastName` only if the user filled them in. Login is a direct `signInWithPassword` call. `src/server/src/middleware/auth.ts` validates the resulting bearer token generically on subsequent domain API calls.

**Google OAuth — code path implemented.** `GoogleSignInButton` (`src/client/src/components/auth/google-sign-in-button.tsx`, used on both signup and login) calls `signInWithOAuth({ provider: 'google', options: { redirectTo: '.../auth/callback' } })` on the browser client, appending `?next=<path>` to that `redirectTo` URL when the login page passed it a `next` prop (see "Post-login redirect to the originally-requested page" below). `src/client/src/app/auth/callback/route.ts` is the PKCE callback: it exchanges the `code` param for a session via a cookie-aware server client (`src/client/src/lib/supabase/server.ts`, `createServerClient` from `@supabase/ssr` reading/writing cookies through `next/headers`), then — same as the email/password login page, see "Onboarding placement quiz" below — redirects to `/onboarding/quiz` if the exchanged user's `app_metadata.onboarding_completed` isn't set, or to `next` (defaulting to `/home`, the `DEFAULT_NEXT` constant) if it is. The onboarding check applies to every `next` value except the password-recovery flow's `next=/reset-password` (checked via `!next.startsWith('/reset-password')`, not an equality check against `DEFAULT_NEXT` — a brand-new Google user following a shared session link still has to complete onboarding first, exactly like the default flow, before landing anywhere else). On failure it redirects to `/login?error=oauth_failed`, or `/forgot-password?error=reset_link_invalid` for a `next=/reset-password` link — no server-side change needed beyond this route, since `src/server/src/middleware/auth.ts` validates any provider's token the same way.

**`config.toml`'s `enabled` flag for Google is a shared, git-tracked setting — not a personal toggle.** `supabase/config.toml`'s `[auth.external.google]` block reads `client_id`/`secret` from the `SUPABASE_AUTH_EXTERNAL_GOOGLE_CLIENT_ID`/`_SECRET` env vars, and `enabled` gates the whole provider — but `config.toml` itself is committed to git. Flipping `enabled = true` and committing it turns Google sign-in on for *every* teammate and CI run, not just the machine that happens to have those two env vars sitting in its own untracked, gitignored root `.env`. **Never commit `enabled = true` without first getting the real credentials into a place every other `supabase start` can reach** (a shared secrets manager, CI secret store, etc.) — otherwise anyone else who pulls the branch gets a `supabase start` that can't resolve the referenced env vars, for a provider they never asked to enable. If you're only testing Google sign-in locally, flip `enabled` back to `false` before committing. The same client_id/secret need to be set separately in the Supabase dashboard for prod (`config.toml` only governs local dev). See README.md "Enabling Google sign-in (optional)" for the full walkthrough and this same warning.

**Password reset — implemented, client-only, deliberately no existence check.** `src/client/src/app/forgot-password/page.tsx` calls `resetPasswordForEmail(email, { redirectTo: '.../auth/callback?next=/reset-password' })` on the browser client and always shows the same "if an account exists, we've sent a link" result regardless of whether the email is registered — Supabase's `resetPasswordForEmail` already behaves this way server-side (always succeeds), and the page intentionally doesn't add a separate "does this user exist" lookup on top of it, since that would require a new service-role-backed endpoint (the installed `@supabase/supabase-js` admin API has no email-filtered user lookup, only paginated `listUsers`) and would turn the form into a user-enumeration oracle. The emailed link reuses the same PKCE `/auth/callback` route as Google OAuth (`next=/reset-password`); on an expired/invalid code, the callback route now branches its failure redirect on `next` — `/forgot-password?error=reset_link_invalid` for this flow, `/login?error=oauth_failed` for OAuth — instead of always assuming Google. `src/client/src/app/reset-password/page.tsx` checks for a session on mount (`getSession()` — the callback route already exchanged the code and set cookies) and, if present, submits the new password via `updateUser({ password })`, then redirects to `/home` since the recovery session is already a full login. `/home`'s own auth guard (see "Client application shell" below) transparently re-routes to `/onboarding/quiz` if that session hasn't completed onboarding yet, so this redirect doesn't need its own onboarding check. Login (`src/client/src/app/login/page.tsx`) links to `/forgot-password` next to the password field.

**`/reset-password` only checks "is there a session," not "did it come from the recovery link" — closed via `secure_password_change`, not app code.** The server-side PKCE exchange in `/auth/callback` means the client-side `PASSWORD_RECOVERY` auth event (which only fires from `detectSessionInUrl`'s hash/URL parsing) never fires in this flow, so there's no client-visible signal to distinguish "just came from the emailed link" from "was already logged in and browsed here directly" — both produce an ordinary valid session that `getSession()` can't tell apart. Rather than fake that distinction client-side (trivially spoofable — anyone can hand-edit a query param), `[auth.email] secure_password_change` in `supabase/config.toml` is set to `true`: confirmed by testing directly against local GoTrue that this checks the session's original auth timestamp (the JWT's `amr` claim, which stays pinned to the original sign-in and doesn't advance on token refresh) and rejects `updateUser({ password })` for sessions that aren't recent — a freshly-exchanged recovery session always qualifies, but a stale pre-existing login doesn't. This is the only place `updateUser({ password })` is called today, so enabling it has no other blast radius, and it's the correct default for any future "change password while logged in" feature too (which should require recent auth regardless of this flow).

**Rate limiting on login/signup/reset — Supabase Auth's own `[auth.rate_limit]`, tuned; app-level limiting deliberately not built.** Login/signup/password-reset all bypass the Hono server entirely (see above), so a Hono rate-limit middleware — the usual fix — would have nothing to intercept; the only enforcement point is Supabase Auth's own config. `supabase/config.toml`'s `[auth.rate_limit]` was tuned down from the CLI's stock scaffolded defaults for brute-force/credential-stuffing resistance: `sign_in_sign_ups` (covers login+signup) `30→10`/5min, `token_verifications` (covers the password-reset link's token exchange) `30→15`/5min; `email_sent` (password-reset emails) tuned *up* `2→3`/hour, since 2 was tight enough to block a legitimate user re-requesting a lost reset email. These are still per-IP only — an attacker distributing attempts across many IPs isn't meaningfully slowed. CAPTCHA (`[auth.captcha]`, hCaptcha/Turnstile) would close that gap but needs a provider account/keys — deferred, see brainstorm.md's Future Features Roadmap. Proxying these three calls through the Hono server (enabling email+IP-keyed limiting, uniform error responses, audit logging) was considered and explicitly declined for now — direct-to-Supabase stays the design; revisit only if per-IP-only limiting proves insufficient in practice.

**`config push`'s per-project overrides — `[remotes.production]` in `config.toml`.** `supabase config push` syncs the *entire* `config.toml` `[auth]` section (not just rate limits) to the linked project, which is a documented CLI gotcha (supabase/cli#3208, #3365): without an override, it would silently overwrite prod's Site URL/Redirect URLs with this file's local-dev values (`127.0.0.1`/`localhost`) on every push. `config.toml` has a commented `[remotes.production]` template pinning `project_id`/`site_url`/`additional_redirect_urls` for exactly this reason — see README.md "Production setup" for when to fill it in and the requirement to keep it in sync with the dashboard's Site URL/Redirect URLs (step 6) if that's ever changed by hand.

**Redirect URL allow-list needs a wildcard per non-`site_url` host.** `supabase/config.toml`'s `additional_redirect_urls` comment says it takes "*exact* URLs" — confirmed by testing directly against local GoTrue: `site_url` (`http://127.0.0.1:3000`) permits any subpath, but an `additional_redirect_urls` entry only matches paths under it if written with a trailing `/**` wildcard; a bare origin only matches that exact URL with no path/query. The Next.js dev server is equally reachable at `127.0.0.1:3000` and `localhost:3000`, and Playwright's `baseURL` (`playwright.config.ts`) uses `localhost`, so `http://localhost:3000/**` and `https://localhost:3000/**` are both listed — without the wildcard suffix, `resetPasswordForEmail`'s `redirectTo` (or any future redirect-based flow reached via `localhost`) silently falls back to `site_url` and drops the `next` param, landing the user on `/?code=...` with a token nothing consumes. Applying a `config.toml` auth change requires `supabase stop && supabase start` to take effect (`supabase start` alone doesn't re-read it).

## Client Application Shell

**`/home` — implemented.** The authenticated landing page (`src/client/src/app/home/page.tsx`). `/` stays the public marketing landing page (unauthenticated, server-rendered, unchanged) — the two are deliberately separate routes rather than one route branching on auth state, so an anonymous visit to `/` never has to know about dashboard data. Every post-auth flow (email/password login, Google OAuth's `DEFAULT_NEXT`, onboarding quiz finish/skip/already-completed, password reset) lands here instead of `/` — see "Auth" above for each flow's specific redirect.

**Auth guard — `useRequireAuth` (`src/client/src/lib/hooks/use-require-auth.ts`).** Client-side hook shared by `/home` and every other page behind `AppShell`: on mount, checks `supabase.auth.getSession()` and redirects to `` `/login?next=${encodeURIComponent(pathname)}` `` if there's no session, or `/onboarding/quiz` if the session's `app_metadata.onboarding_completed` isn't set — same two-part check `onboarding/quiz/page.tsx` already did inline, generalized so every gated page doesn't reimplement it. Callers render `null` until the hook returns a non-null `{ accessToken, userId }`, matching the quiz page's existing pattern. This auth check itself is still a client-side redirect, not edge middleware — `src/client/src/middleware.ts` exists, but only to refresh an expiring Supabase session cookie before Server Components/Route Handlers read it (see "Auth" above); it doesn't gate routes or redirect unauthenticated requests. So an unauthenticated direct nav to `/home` (or any gated page) briefly resolves the route before `useRequireAuth`'s effect fires, rather than being blocked at the edge. Acceptable since no sensitive data renders before the guard redirects — the page returns `null` until `useRequireAuth` resolves.

**Post-login redirect to the originally-requested page.** `useRequireAuth`'s `next` query param (above) is read back by `login/page.tsx` and, once sign-in succeeds and onboarding is already complete, used in place of the default `/home` redirect — so clicking a shared session link while logged out lands back on that exact session after logging in, instead of the dashboard. `next` is untrusted input on `/login` (reachable by anyone, not just links this app generated), so it's validated by `lib/safe-next-path.ts`'s `isSafeNextPath` — must start with a single `/`, not `//` or `/\` (both browsers treat as protocol-relative), and contain no `://` — before use; an unsafe value is silently dropped in favor of `/home`. The same validated `next` is forwarded into `GoogleSignInButton`'s OAuth `redirectTo` (see "Google OAuth" above) so the Google sign-in path gets the same behavior. **Deliberately not threaded through the onboarding quiz** — a first-time user who hits a gated page while logged out still gets `/login?next=...` → login → `/onboarding/quiz` → finish/skip → `/home`, same as before this feature; only an already-onboarded user's `next` survives all the way back to the original page. Revisit only if that gap turns out to matter in practice.

**Nav shell — `AppNav` + `AppShell` (`src/client/src/components/nav/`).** `AppNav` renders four destinations, in order: **Home** (`/home`, the dashboard), **Sessions** (`/sessions`), **Nearby venues** (`/venues`), **Profile** (`/profile`) — as a fixed bottom tab bar below the `sm` breakpoint and a fixed left sidebar at `sm` and up (icon-only between `sm` and `lg`, icon+label at `lg`+) — mobile-first per design-system.md's Platform section. `AppShell` wraps `AppNav` with the shared header (just a `Pavilion` logo linking back to `/home`, redundant with the Home nav item but kept as a conventional top-left brand link) and content padding that clears whichever nav variant is active. `/home`, `/venues`, `/sessions`, `/profile` all render through `AppShell` so the nav and header are consistent across the authenticated app. Player search was originally the fourth nav slot; it was replaced with Home (a way back to the dashboard from any other authenticated page) once the nav grew to include Profile, and `/players` was pushed out to stay unlinked rather than the nav growing to five items.

**`/venues` — stub page, not yet implemented. `/players` — stub page, no longer linked from `AppNav`.** Auth-gated (same `useRequireAuth` guard) placeholder pages. `/venues` exists so `AppNav`'s link resolves to something instead of a 404; no data fetching, no new API endpoints. `/players` still exists at its route (reachable by direct URL) but isn't reachable from the nav anymore — kept rather than deleted since it's still a real planned feature (see brainstorm.md), just not part of the current four-item nav. Build out real venue discovery / player search here when those features are scoped — neither has a listing/search endpoint yet beyond what already exists (`GET /api/venues`; there's no user-listing endpoint at all, see "User profile fields not yet exposed" below).

**`/sessions`, `/sessions/new`, `/sessions/[id]` — implemented: browse/search, RSVP lifecycle, and organizer management.** No new server endpoints — every call is one of the existing `session` domain routes (see "API Endpoints" below). `/sessions` (`src/client/src/app/sessions/page.tsx`) has three tabs — **Browse** (public sessions, no organizer/attendee filter), **Hosting** (`organizer_id=<self>`), **Attending** (`attendee_id=<self>`) — reusing the same `GET /api/sessions` query params `/home`'s dashboard widgets already call, plus a status selector (`upcoming`/`completed`/`cancelled`) and, on Browse only, `SessionFilters` (`components/session/session-filters.tsx`). Session list items render via `SessionCard` (`components/session/session-card.tsx`); there's deliberately no per-card spot count (`GET /api/sessions` doesn't return RSVP counts, and fetching one per card would be an N+1 call) — spot count only appears on the detail page, where the RSVP list is already fetched.

**Browse filters are editorial, not boxed** — Search and Date stay inline as always-visible primary controls (underline inputs, `components/session/field-styles.ts`'s shared `fieldClassName`/`labelClassName`, reused by the create/edit form too); Skill min/max sit behind a "More filters" pill, disclosed via a `Drawer` (`components/ui/drawer.tsx`, Base UI's primitive — bottom sheet, swipe-to-dismiss) below the `sm` breakpoint and a `Popover` dropdown at `sm`+, switched via `@base-ui/react/unstable-use-media-query`'s `useMediaQuery` (same 640px cut line `AppNav` uses). Skill defaults are computed per-user (`computeDefaultSkillRange` — mirrors `joinSession`'s asymmetric RSVP tolerance: floor = grade − 1.5, ceiling = grade + 3.0, clamped to `[MIN_SCORE, UNVERIFIED_CEILING]` = `[1, 7.99]` — a narrower clamp than the `[1, 99.99]` the server's `POST`/`PATCH` validation allows, since this is a sensible *default view*, not the hard limit of what a session can actually be created with), not a fixed global range. **Date is an adaptive range, not a single date:** two `<input type="date">`s (From/To) plus a computed summary caption — `formatDateRangeSummary` (`lib/session-format.ts`) renders "After {date}" with only one bound set, "{date1} – {date2}" with both, "Any date" with neither. An inverted range (`dateTo < dateFrom`) shows an inline destructive-colored warning and blocks auto-apply until fixed — checked as plain `YYYY-MM-DD` string comparison, no `Date` parsing needed. `date_to` is sent as end-of-day (`endOfDayIso`), not midnight, so the upper bound doesn't exclude same-day sessions.

**Search filters by venue name or exact session id, not city — single input, client-side auto-detected.** `SessionFilters`' "Search" field (`session-filters.tsx`) replaced the earlier plain-text City filter. `sessions/page.tsx`'s query-building effect checks the trimmed value against a UUID regex (`isSessionId`, `lib/session-format.ts`) — a match sends it as `id`, anything else as `name` — rather than exposing two separate inputs. This is what lets a shared session link's UUID typed or pasted into Browse surface an `invite_only` session that a plain-text venue-name search intentionally can't (see the `GET /api/sessions` endpoint doc above) — pasting a session's own id is treated as "the caller already has this specific link," not a generic text search.

**Browse filters are reactive, not submit-driven.** `SessionFilters` auto-applies the whole filter set (search, date, skill) `APPLY_DEBOUNCE_MS` (400ms) after the last change, instead of requiring an explicit Search/Apply click — one shared debounce timer per component, so a burst of edits across multiple fields still collapses into a single `GET /api/sessions` call rather than one per field. There is deliberately no separate submit button anymore; the previous "Search" pill and the More-filters popover/drawer's "Apply" button were both removed as redundant once every field applies on its own. A `lastAppliedRef` (serialized JSON of the last-applied filter set) skips re-firing when the pending value is identical to what's already applied — true on mount, and immediately after "Reset to defaults" (which applies synchronously, bypassing the debounce) — so neither of those cases wastes an extra request.

`/sessions/new` and the inline "Edit session" form on `/sessions/[id]` share one field-rendering component, `SessionFormFields` (`components/session/session-form-fields.tsx`), since `SessionUpdateFields` (server) is `SessionCreateFields` minus `type`/`venueId`/`isRecurring`/`recurringCronExpr` — the component takes a `mode: 'create' | 'edit'` prop that only hides the `type` selector, nothing else differs. Venue selection is **free-text `venueName` only** — no picker against `GET /api/venues`, since `/venues` is still a stub; matches brainstorm.md's "unofficial venue, organizer posts it directly" case. `isRecurring`/`recurringCronExpr`/`strictRange` are not exposed in either form — recurring child-session spawning and `strict_range` enforcement are both server-side not-yet-built (see "Session domain" and "Skill range enforcement" below), so there's nothing to consume those inputs yet.

**Form layout: categorical fields grouped first, numeric/text fields after — a deliberate section split ("Session details" / "Logistics"), not incidental ordering.** Every `RadioGroup`-based field (type, format, visibility, shuttle policy) renders in one block above every numeric/text/date field (venue name, skill min/max, court count, max players, starts-at, duration, tube price, notes), so a user's multiple-choice taps all happen before any typing or scrolling starts. `emptySessionFormValues()` seeds a new create form with context-aware, non-blank defaults rather than starting empty: `skillMin`/`skillMax` = `3.0`/`5.0` (brainstorm.md's own worked example under "Session skill range enforcement" — "e.g., 3.0–5.0"), `courtCount` = `1`, `maxPlayers` = `8`, `durationMinutes` = `60`, and `startsAt` defaults to tomorrow evening (`defaultStartsAtLocal` — also sidesteps ever holding an empty `startsAt`, which would otherwise crash `new Date('').toISOString()` on submit).

**`starts_at` uses `StartsAtPicker` (`components/session/starts-at-picker.tsx`), not a bare `<input type="datetime-local">`.** Mobile browsers often render `datetime-local` as fiddly nested year/month/day/hour/minute segments — this splits the same underlying `YYYY-MM-DDTHH:mm` value into a native `<input type="date">` (mobile browsers already give that a clean calendar/wheel UI) plus one-tap time-of-day pills for common slots (`06:00`–`21:00`) with a native `<input type="time">` fallback for anything off that list. Disclosure follows the exact same responsive Drawer/Popover split as `SessionFilters`'s "More filters" — the trigger itself is styled as an underline form field (not a pill) showing the computed `formatSessionDateTime` summary, so it reads as one of the form's own inputs rather than a separate widget.

`/sessions/[id]` resolves organizer/attendee display names from the session-scoped endpoints themselves, not a client-side fan-out: `GET /api/sessions/:id` returns an additional `organizerName` field and each row in `GET /api/sessions/:id/rsvps` carries its own `displayName`, both resolved server-side by `session.service.ts` (see "Privacy — shared-session name exception" below). A `null` name (caller isn't a participant and the target profile is private) falls back to a generic "A Pavilion user"/"a Pavilion user" label client-side rather than blocking the page. RSVP actions (Join/Cancel) and organizer actions (Edit, Cancel session, status progression, attendance marking) all use inline confirm states rather than a dialog primitive — no `dialog` component is installed, and this matches the app's existing preference (see profile page's edit toggle) for inline state over a new modal dependency. The "cancelling within 12h costs reliability points" warning on the Cancel-RSVP confirm step is computed client-side from `starts_at` — the API itself only signals this on the rare `penalty_not_applied` failure path, not on an ordinary successful late cancel.

**Share button copies the page URL, client-only, no backend involvement.** Sits inline just below the "Hosted by" line (`window.location.href`). Confirmation is a transient `role="status"` popup positioned above the button (same `bg-popover`/`shadow-md`/`ring-1 ring-foreground/10` styling as `InfoTooltip`'s popup, but plain absolutely-positioned CSS rather than Base UI's `Popover` — a controlled, non-hover, non-click-toggle show/hide didn't fit that primitive's trigger model), shown for 1s via `setTimeout`. The button's own label never changes ("Share" throughout) — only the transient popup communicates the copy succeeded.

**Copy path falls back to `execCommand('copy')` when the Async Clipboard API is unavailable.** `navigator.clipboard` only exists in a secure context — `https:`, or `http:` on `localhost`/`127.0.0.1` — so it's `undefined` in Safari when the app is reached over a plain-http LAN IP, e.g. testing on a phone via `http://192.168.1.x:3000`. Found by testing the Share button on an actual iPhone over Safari, where it silently did nothing; Chrome's desktop mobile-device emulator didn't catch this since it's served from `localhost`, which never hits the restriction. `handleShare` now checks `navigator.clipboard?.writeText` first and falls back to a temporary off-screen `<textarea>` + `document.execCommand('copy')` (no secure-context requirement) if it's unavailable or rejects.

**Privacy — shared-session name exception, implemented.** `getSessionRsvps` and `getSessionOrganizerName` (both `session.service.ts`) special-case any caller who is themselves an active participant of the same session — the organizer, or a `going`/`waitlisted`/`attended` attendee — so that caller sees every co-attendee's and the organizer's display name regardless of `privacy_level`, matching brainstorm.md's Privacy section ("only a player's name/display name is visible to anyone who's shared a session with them"). Anyone else (including an anonymous browser of a public session) still only sees names for `public` profiles. `getUserById` (`user.service.ts`) is deliberately untouched — this carve-out is session-scoped, not a change to general profile visibility. This fixed the undercounting bug where a fresh account's `private`-by-default profile left the Going list, spot count, and organizer name blank even on the account's own sessions.

**`/profile` — implemented, view + edit + logout.** `src/client/src/app/profile/page.tsx`, reached via `AppNav`'s fourth destination. View mode composes the caller's own data from two existing endpoints — `GET /api/users/:id` (name, city/region, preferred formats, play style, privacy level, member-since) and `GET /api/ratings/user/:userId` (grade, subtier, provisional flag, unverified-ceiling flag) — no new endpoint, and no `getUserProfile()`-style aggregation was added (see "User profile fields not yet exposed" below: `reliabilityScore`/`sessionCount` still aren't exposed by any endpoint, so they don't appear here either). The rating row renders `Grade {grade}` next to a 4-star indicator (filled up to `subtier`) rather than the API's roman-numeral `label` string, which is unused on this page. When `rating.isProvisional` and/or `rating.atUnverifiedCeiling` are true, badges next to the stars each carry an `InfoTooltip` (design-system.md's Component Library) explaining what that means in plain language — the API returns both as plain booleans with no explanatory text, so the copy lives entirely client-side.

**Edit mode covers every editable `PATCH /api/users/:id` field except `photoUrl`.** The endpoint accepts `displayName`, `firstName`, `lastName`, `photoUrl`, `city`, `region`, `preferredFormats`, `playStyle`, `privacyLevel`; this page's "Edit profile" form exposes all but `photoUrl` (no upload flow exists yet — that's the only exclusion). `firstName`/`lastName` are optional text inputs, sent as `null` rather than `''` when cleared (`fields.firstName.trim() || null` in `handleSave`) so clearing the field in the UI actually nulls the column instead of writing an empty string. City/region (labeled "State" — see database-schema.md) round out the rest.

**Verified users' names are locked — app-layer rule, not just the DB constraint.** `updateUser` (`user.service.ts`) rejects with `{ ok: false, reason: 'name_locked' }` — surfaced by `user.router.ts` as `403` — for any `PATCH` that includes `firstName` or `lastName` at all once `profiles.verified_tier` is set, regardless of whether the new value actually differs from the current one. This is stricter than `profiles_verified_requires_name` (which only blocks *clearing* the name to null — see "Verification approval action" below): once verified, the name is checked against real credentials, so allowing it to change to a *different* non-null value afterward would just as easily decouple the verified badge from the identity it verified. `ProfilePage`'s edit form mirrors this: `firstName`/`lastName` inputs are `disabled` with an `InfoTooltip` explaining why whenever `user.verifiedTier != null`, and `handleSave` omits both keys from the request body entirely in that case (`const { firstName, lastName, ...rest } = fields`) rather than sending them unchanged — sending them at all, even unchanged, would trip the router's `403` and block saving *any* field, since the check is presence-based rather than diff-based. Verified against a real Postgres instance in `user.integration.test.ts` (clearing, changing, and — the control case — editing an unrelated field on a verified profile all behave as expected).

**State field is a searchable `Combobox`, constrained to real US states — not free text.** `src/client/src/lib/us-states.ts` exports the 50 states + DC as `{ value, label }` pairs (USPS two-letter code as `value`, matching what's stored in `profiles.region` and what the "Location" view already displays, e.g. "Rockville, MD"); `region` city stays free-text `Input` since there's no comparably small closed set for cities. Selecting an option sets `fields.region` to that state's code; clearing it sets `''`. This is a client-side constraint only — `user.router.ts`'s `region` validation (above) still just checks `typeof region === 'string'`, so a non-web caller could still send an arbitrary string. Tightening that to an enum check was considered and deliberately skipped: state codes aren't currently used in any query logic (unlike `playStyle`/`privacyLevel`/`preferredFormats`, which drive filtering/branching elsewhere), so a bad value here is a display-quality issue, not a correctness one — revisit if that changes (e.g. state-based session/venue filtering gets built).

**`PATCH /api/users/:id` is mass-assignment-safe by construction, not by validation.** `updateUser` (`user.service.ts`) never spreads the request body into the DB update — it's nine explicit `if (fields.x !== undefined) updates.x_column = fields.x` lines, one per editable column. A request body containing `internalScore`, `verifiedTier`, `ratingFloor`, `reliabilityScore`, or any other column is structurally inert: `updateUser` never reads those properties, so they can't reach the `UPDATE`, regardless of what validation does or doesn't exist in the router. Confirmed against a real request in this session (crafted PATCH with rating/trust fields alongside a legit `displayName` — only `displayName` changed). This means the request-body validation added in `user.router.ts` (below) is defense against bad *values* for the nine allowed fields, not a privilege-escalation backstop — that backstop already existed structurally.

**Request-body validation — `user.router.ts`'s `PATCH /:id`, implemented.** Previously the router parsed the body and passed it straight to `updateUser` with no checks, so `preferredFormats`/`playStyle`/`privacyLevel` could be written as any string (or `preferredFormats` as a non-array) since nothing validated them before the DB write — invalid-value risk, not the privilege-escalation risk above (see previous paragraph for why those are different). Now validates each of the nine editable fields before calling `updateUser`, `400`ing on the first failure: `displayName` non-empty string; `firstName`/`lastName`/`photoUrl` string-or-null; `city`/`region` string; `preferredFormats` an array whose members are all in `['singles', 'doubles', 'mixed']`; `playStyle` in `['competitive', 'social', 'training']`; `privacyLevel` in `['private', 'public']` — same explicit-allow-list-array style as `session.router.ts`'s `VALID_STATUSES`/etc. Covered in `user.router.test.ts` via a parameterized `it.each` over invalid values per field, plus a dedicated test asserting `mockFrom` is never called (i.e. validation short-circuits before any DB call) and one confirming out-of-set fields like `internalScore` are silently dropped rather than rejected (matches the mass-assignment-safety paragraph above — they're not invalid input, they're not input the endpoint reads at all).

**Logout** (`supabase.auth.signOut()` on the browser client, then `router.replace('/')`) sits inline next to "Edit profile" in view mode — both are the account-action row at the bottom of `/profile`'s view state, not part of `AppNav`'s primary navigation, and hidden while the edit form is open (replaced by that form's own Save/Cancel row). Styled `variant="destructive"` (the existing pastel-red token, `bg-destructive/10 text-destructive` — see design-system.md's Color Palette) with a `LogOut` icon, matching the design system's "icon-marked, muted-severity" pattern for an action that's consequential but not dangerous enough for a hard-red confirm-to-proceed treatment.

**`/home`'s dashboard widgets — reuse `GET /api/sessions`, no new endpoints.** "Next session" fetches `attendee_id=<self>&status=upcoming` and `organizer_id=<self>&status=upcoming` in parallel and takes the earliest `startsAt` across both (the endpoint doesn't support an attendee-OR-organizer filter or server-side sorting, so both the merge and the sort happen client-side). "Recent activity" fetches `attendee_id=<self>&status=completed`. `listSessions`' `attendee_id` filter (`session.service.ts`) resolves via `session_rsvps` rows `.in('status', ['going', 'waitlisted', 'attended'])` — `attended` was added alongside the original two so a session survives this filter after the organizer runs `POST /:id/attendance` (which flips `going` → `attended`); without it, marking attendance would silently drop a completed session out of the attendee's own history. `no_show`/`cancelled` are deliberately excluded — this filter answers "sessions this user was actually part of," not "sessions this user RSVPed to at some point." Both the "Next session" card and each "Recent activity" row are wrapped in a `next/link` `Link` to `/sessions/${session.id}` — fixed after shipping as a click-through-to-nothing gap; not just visual list items.

**"Friends activity" is a placeholder, not real data.** There's no followers/friends relationship in the schema (`database-schema.md`'s Excluded section lists "Follower graph" as a future feature; `brainstorm.md`'s Future Features Roadmap has the same item, version TBD), so the dashboard section is an empty "coming soon" state rather than fabricated content — consistent with design-system.md's "No fabricated trust signals" UX principle. Wire this up once a followers/friends concept actually exists; don't approximate it with session co-attendees or any other proxy without revisiting that product decision first.

## Security Headers & CORS

**CORS — API-side, `src/server/src/index.ts`.** Replaced the earlier open `cors()` default with an explicit allow-list read from `ALLOWED_ORIGINS` (comma-separated, no wildcard support — see `.env.example`), defaulting to `http://localhost:3000,http://127.0.0.1:3000` in dev. Also restricts `allowMethods` to `['GET', 'POST', 'PATCH', 'DELETE']` and `allowHeaders` to `['Content-Type', 'Authorization']`. Prod sets this to the actual frontend domain(s) — see README.md "Production setup (one-time)" for the env var walkthrough.

**Both `localhost` and `127.0.0.1` need their own entry — CORS checks the browser's `Origin` header, not the destination.** The Next.js dev server binds `0.0.0.0`, so it answers on either host, but a browser that navigated to `http://127.0.0.1:3000` sends `Origin: http://127.0.0.1:3000` — a distinct string from `http://localhost:3000` as far as the allow-list's `.includes()`-style check is concerned, even though the client always calls the same explicit `NEXT_PUBLIC_API_URL` regardless of which host served the page. Missing the `127.0.0.1` entry surfaces as every API-backed page (e.g. `/home`, `/profile`) failing with a browser-console CORS error and no data loading, while the exact same page works fine under `localhost`. Same root cause as "Redirect URL allow-list needs a wildcard per non-`site_url` host" above, for a different subsystem (this is `ALLOWED_ORIGINS`/Hono `cors()`, that's Supabase's `additional_redirect_urls`) — both exist because `localhost` and `127.0.0.1` are, correctly, treated as different origins by browsers even when they resolve to the same machine.

**Cache-Control — API-side, `src/server/src/middleware/no-store.ts`.** `noStore` middleware sets `Cache-Control: no-store` + `Pragma: no-cache` on every `/api/*` response, applied in `index.ts` (`app.use('/api/*', noStore)`). Prevents an intermediary (browser, proxy, CDN) from caching a response fetched under one caller's `Authorization` header and serving it to a different caller — relevant since most endpoints return per-user data (profiles, ratings, RSVPs).

**Optional-auth resolution — `getOptionalUserId(c)` in `src/server/src/middleware/auth.ts`.** For routes that behave differently for logged-in vs. anonymous callers without requiring auth outright (e.g. gating `invite_only` visibility, resolving a caller identity for privacy filters) — resolves to `undefined` rather than rejecting when no token is present or it's invalid. `session.router.ts`'s `GET /`, `GET /:id`, and `GET /:id/rsvps` use it instead of importing `supabase` directly to call `supabase.auth.getUser`, keeping auth resolution behind the `auth` middleware module rather than leaking a service-layer import into routers. Follow this pattern for any future optional-auth need instead of reaching for `supabase` directly in a router.

**Content-Security-Policy — client only, Report-Only for now.** Set via `headers()` in `src/client/next.config.ts`, applied to every route (`source: '/(.*)'`). Not added to the Hono API (`src/server`) — it only returns JSON, where CSP has no effect.

- Directives: `default-src 'self'`, `script-src 'self'`, `style-src 'self'` (no `'unsafe-inline'` — the one inline `style={{}}` in `google-sign-in-button.tsx` was moved to a `.font-google-sans` class in `globals.css` specifically so this could stay strict), `img-src 'self' data:`, `font-src 'self'` (Nunito is self-hosted at build time via `next/font/google`, so no `fonts.googleapis.com`/`fonts.gstatic.com` needed), `connect-src 'self' <NEXT_PUBLIC_SUPABASE_URL> <NEXT_PUBLIC_API_URL>`, `frame-src 'none'`, `object-src 'none'`, `base-uri 'self'`, `form-action 'self'`, `frame-ancestors 'none'` (app is never embeddable).
- `connect-src`'s Supabase/API origins are read from `process.env.NEXT_PUBLIC_SUPABASE_URL`/`NEXT_PUBLIC_API_URL` at build time in `next.config.ts` (Next loads `.env.local` before evaluating the config file) — not hardcoded, so each environment's build picks up its own values.
- Google OAuth sign-in (`GoogleSignInButton`) needs no `script-src`/`frame-src` exception — it's a full-page redirect via `supabase.auth.signInWithOAuth`, not an embedded widget.
- **Report-only, no `report-uri`/`report-to` yet** — violations currently only surface in browser devtools during manual QA. A collection endpoint is deferred, see brainstorm.md's Future Features Roadmap. Promote to enforced (`Content-Security-Policy`) once this has run report-only for a while with no unexpected violations.
- **Will need revisiting once `messaging` (Stream Chat) is implemented** — the client-side Stream Chat SDK will need its own `script-src`/`connect-src` (and likely `wss:`) origins added; nothing messaging-related is in the policy today since no Stream Chat client code exists yet (see "Messaging" below).

## Rating System

Implemented in `src/server/src/domains/rating/`. Core scoring (`computeRatingUpdate`, `toRatingDisplay`) lives in `rating.algorithm.ts` — pure, no Supabase import — and is re-exported from `rating.service.ts`, which adds the DB orchestration (`submitRating`, `getRatingHistory`, etc.). The split means the algorithm is unit-testable, and runnable standalone (see `rating.demo.ts`), without a DB connection.

**Scope note:** the `verification_requests` admin approve/reject flow (submit evidence → admin review → `verified_tier`/`rating_floor` written to `profiles`) is **not yet implemented** — those columns exist and are read/respected by the scoring algorithm (see Rating locks below), but nothing in the app currently writes them. Until that flow exists, they're only settable via direct DB access.

**Session eligibility precondition:** before any duplicate/participant checks, `submitRating` fetches the session's `starts_at`/`status` and rejects with `session_not_eligible` if the session is `cancelled` or hasn't started yet (`starts_at` in the future) — peer ratings can only be submitted for sessions that have actually happened. A session that doesn't exist returns `not_found`.

**Duplicate-vote race:** `submitRating`'s duplicate check is an app-level pre-read of `session_rating_submissions` before insert, not a DB-level catch — `session_rating_submissions` carries `UNIQUE(session_id, rater_id, ratee_id)` as the actual backstop. Two concurrent submissions for the same vote can both pass the pre-check; the insert's `{ error }` is checked and treated as `{ reason: 'duplicate' }` specifically so the loser of that race aborts before any score-update logic runs, rather than silently double-applying the vote. Covered by `src/server/src/__integration__/rating.integration.test.ts` (see Testing below) — this scenario only reproduces against a real unique-constraint violation, not the mocked unit suite.

**Data model considerations:**
- Store raw internal score (float, 1.0–10.0+) separately from displayed tier/subtier
- Display tier is derived: `grade = floor(score)`, `subtier = floor((score % 1) / 0.25) + 1` (1–4), clamped to 1–4 as a defensive bound against floating-point edge cases. Floor-based bucketing (not round-to-nearest) gives every subtier an equal 0.25-wide band — rounding instead would give the top subtier a double-width band (`[0.625, 1.0)`) while the bottom subtier got a half-width band (`[0, 0.125)`), silently collapsing distinct scores (e.g. `7.70` and `7.99`) into the same displayed subtier
- Display label format: `"Grade {grade} — {I|II|III|IV}"` (roman numeral per subtier)
- Never expose raw float to the client — only grade + subtier label via `GET /api/ratings/user/:userId`. Auth-gated and privacy-aware: returns 404 if the target profile's `privacy_level` is `'private'` and the requester isn't the owner, matching `user.service.ts`'s `getUserById` privacy behavior for the same underlying profile
- `toRatingDisplay` also derives `atUnverifiedCeiling` (`verifiedTier === null && grade === 7 && subtier === 4`) so the client can prompt an unverified player to seek verification as soon as they reach the ceiling grade's last subtier — not only once the score is actually clamped at 7.99 — since a player at 7.8 is just as stuck as one pinned at 7.99 (see brainstorm.md's "Verification prompt UX"). `ProfilePage` shows this as an `InfoTooltip` badge next to the star rating, the same pattern as the `isProvisional` badge. `verifiedTier` defaults to `null` when omitted (`completeOnboarding`'s callers never pass one, since a player can't be verified before their first score exists)
- **Vote attribution is never exposed**, to anyone, via the API — not even to the ratee themselves. `session_rating_submissions` (rater_id ↔ vote) is write-only through the rating domain's endpoints. `GET /api/ratings/user/:userId/history` (self-only) surfaces only the aggregated per-session `score_before/score_after/delta` from `rating_history`, never which rater(s) drove it or what they voted
- Keep full rating history per user (every session's delta) for audit, appeals, anomaly detection

**Scoring algorithm (per vote, computed and applied immediately on submission — not batched per session):**

1. Vote → offset (internal-score units): `much_stronger=+1.0, stronger=+0.5, about_equal=0, weaker=-0.5, much_weaker=-1.0`. `did_not_play` is recorded but has no scoring or familiarity effect.
2. `sessionAnchor` = average `internal_score` of all profiles with a `'going'` RSVP on the session.
3. `impliedTarget = sessionAnchor + voteOffset` — the vote asserts the ratee belongs at this point relative to the group.
4. Learning rate: `0.12` normally, `0.35` while the ratee is in placement (`placement_sessions_remaining > 0`).
5. Weight = `proWeight * calibrationWeight * familiarityWeight`:
   - **Pro weight:** rater grade `floor(raterScore) >= 8` → `1.5x`, but **only for downward/neutral votes** (`voteOffset <= 0`); upward votes from a pro get no boost (`1.0x`) — a pro can't unilaterally manufacture a rating increase, only corroborate one.
   - **Calibration weight:** if `|raterScore - rateeScore| > 2.0` grades, weight decays linearly (`-0.25` per grade over the threshold) down to a floor of `0.25` — a rater's judgment is unreliable far outside their own level.
   - **Familiarity weight (recency-adjusted):** `recencyFactor = 0.5 ^ (daysSinceLastRated / 60)` (60-day half-life, `0` if no prior pairing); `effectivePairCount = pair_count * recencyFactor`; `weight = 1 / sqrt(effectivePairCount + 1)`. Repeated *recent* pairings decay weight (the 15th game tells you little after the 5th), but a long gap resets it toward fresh — a rater's prior familiarity shouldn't keep suppressing their input if the ratee has had time to improve since.
6. `delta = learningRate * weight * (impliedTarget - rateeScore)`, clamped to `±1.0` during placement / `±0.5` otherwise (hard cap on single-vote swings).
7. `newScore = rateeScore + delta`, then: floor-clamp to `rating_floor` if set, ceiling-clamp to `7.99` if `verified_tier` is null, floor-clamp to `1.0`, round to 2 decimals. `delta` in `rating_history` is recomputed post-clamp (`newScore - rateeScore`) so the audit trail reflects what actually happened.
8. `placement_sessions_remaining` decrements once per `(session, ratee)` — on the *first* submission row for that pair, regardless of how many raters eventually submit — not once per vote.

**Anomaly detection (flag for review, not a block):**
- `session_rating_submissions.flagged = true` when `|raterScore - rateeScore| > 2.0` grades (same calibration distance used for weight decay above)
- **Out of scope / deferred:** same rater-ratee pair exceeding N sessions without fresh raters in between (partially mitigated by the recency-adjusted familiarity weight above, but not flagged), coordinated voting pattern detection, and global distribution recalibration — these need batch/cron analysis, not per-request logic

**Distribution calibration:**
- Target: slightly right-skewed normal, bulk of active users landing 3.5–4.5
- May need a global recalibration mechanism if the distribution drifts over time (e.g., grade inflation) — not implemented; would be a periodic admin/cron job, not part of the live scoring path

**Rating locks:**
- User record stores `verified_tier` (nullable) and `rating_floor` (nullable float)
- On any rating update: `new_rating = max(new_rating, rating_floor)` if floor is set
- `verified_tier` is set by admin/verification flow — not derivable from peer ratings alone (flow not yet built, see Scope note above)
- Unverified users are hard-capped at `7.99` — the algorithm simply cannot write a value ≥ 8.0 without a verified_tier on the record

**Tier-boundary protection (demotion/promotion):**
- Problem: applying every vote's delta immediately means a player hovering right at a whole-number grade boundary can flicker back and forth across it session to session. A naive fix — delay the *displayed* grade while letting raw `internal_score` keep moving underneath — just relocates the problem: when the delayed change finally lands, the score has often drifted well past the boundary, so the displayed grade can skip subtiers or even whole grades instead of landing just past the line like a real single-tier transition should.
- Fix: clamp the **raw score itself** at the grade boundary the moment a vote would cross it, instead of letting it drift while only the display lags. `profiles` stores `demotion_protection_started_at` / `promotion_protection_started_at` (both nullable timestamptz) to track this.
- Mechanism (in `computeRatingUpdate`, after the existing absolute locks — `rating_floor`, the 7.99 ceiling, `MIN_SCORE` — are applied to get the natural new score): `currentGrade = floor(rateeScore)` (the score *before* this vote).
  - **Demotion** triggers when the natural score would land `< currentGrade`. First trigger → pin at `currentGrade` exactly, start the clock. Each further sub-floor vote while the window hasn't elapsed → pin at `currentGrade` again (the clock is *not* reset per vote — it's measured from the first trend, not "consistently weak every single vote"). Once `DEMOTION_PROTECTION_WINDOW_DAYS` (7) full days have elapsed while still trending weak → release: score drops to `currentGrade - 0.01`, landing exactly at subtier IV of the grade below, never skipping.
  - **Promotion** mirrors this exactly (own state, same shape) for crossing `>= currentGrade + 1`, pinning at `currentGrade + 1 - 0.01` while protected and releasing to exactly `currentGrade + 1` (subtier I) after `PROMOTION_PROTECTION_WINDOW_DAYS` (3) full days.
  - **Windows are intentionally asymmetric** even though the mechanism is symmetric: demotion (7 days) is more generous than promotion (3 days) by design. Symmetric *mechanism* matters because demotion-only protection would make tiers easy to enter and sticky to leave — a one-way ratchet feeding the exact grade-inflation drift risk noted above. The shorter promotion window reflects that climbing should still require less sustained proof than falling gets forgiveness for.
  - **Recovery cancels immediately:** if a vote pulls the natural score back across the boundary while protected, the protection clears right away and the natural score applies as-is — no protection debt carries over.
  - **Skipped entirely during placement** (`isPlacement`) — placement explicitly wants fast convergence to true level, which this would fight.
  - A single vote, however large, can only ever pin at the boundary — it cannot blow through multiple grades in one shot. This falls out of the design rather than needing a special case.
  - Elapsed time is counted in **full calendar days, ignoring time-of-day** (e.g. 3:00pm June 1 → 2:30pm June 8 = 7 elapsed days, not 6) — deliberately coarser than, and independent of, the millisecond-precise familiarity-decay day count used elsewhere in the algorithm.
- `toRatingDisplay` needs no changes — it already derives grade/subtier from whatever `internal_score` currently holds, and a pinned or just-released score produces a correct label through the existing formula. The mechanism is entirely contained to the score-update path; protection state is never exposed via the API.

**Onboarding placement quiz — implemented in `rating.algorithm.ts`/`rating.service.ts`/`rating.router.ts`, no new domain.** The quiz's only output is an initial placement score, which is exactly what `rating` already owns — folding it in here avoids a domain that would only ever write one column.

- **Scoring:** 4 self-reported multiple-choice questions (`highest_level_played`, `strongest_opponents`, `competitive_history`, `play_frequency`), each option mapped to a fixed score in `ONBOARDING_OPTION_SCORES` (`rating.algorithm.ts`). `computeOnboardingScore` averages the 4 mapped values, clamps to `[MIN_SCORE, UNVERIFIED_CEILING]` (same bounds `submitRating` uses), and rounds to 2dp. Returns `null` — surfaced as `400 invalid_answers` — if any of the 4 keys is missing or its value isn't a recognized option id; checked explicitly because a missing key would otherwise silently skew an *average* rather than erroring. "Self-assessed weaknesses" (mentioned in brainstorm.md) is intentionally not part of the quiz — it's diagnostic, not a skill-level signal, and nothing downstream reads it yet.
- **Calibration is approximate**, same caveat as "Distribution calibration" above — revisit via the already-deferred global recalibration job if drift shows up, not by hand-tuning the option-score table later.
- **Skip default:** `SKIP_DEFAULT_SCORE = 2.75`, one grade below `AVERAGE_RATING_ANCHOR = 3.5` (the low end of brainstorm.md's stated 3.5–4.5 "average active user" range).
- **Write path (`submitOnboardingQuiz` / `skipOnboarding`):** both go through a shared `completeOnboarding` helper — a claim-style atomic `UPDATE profiles SET internal_score, onboarding_completed_at = now() WHERE id = :userId AND onboarding_completed_at IS NULL AND deleted_at IS NULL`, the same shape as `venue.service.ts`'s `claimVenue` (fold the precondition into the `UPDATE`'s `WHERE` rather than a separate `SELECT`-then-`UPDATE`) — a 0-row result means onboarding was already completed (`409 already_completed`), including races against a concurrent submit/skip from another tab. Unlike `claimVenue`, this race is actually verified against a real Postgres instance, not just asserted by pattern similarity: `src/server/src/__integration__/rating.integration.test.ts`'s `completeOnboarding` suite fires two concurrent calls (skip-vs-skip, and submit-vs-skip) with `Promise.all` and asserts exactly one wins — see Testing below. `placement_sessions_remaining` is left untouched (already defaults to 3 at signup): quiz-takers and skippers both stay in placement mode identically, since "first 3 sessions are placement matches" applies regardless of how the initial score was set.
- **Audit trail:** `onboarding_quiz_responses` (answers, computed score, skipped flag) — mirrors why `rating_history` exists for peer votes. Best-effort insert once the `profiles` update has committed; never read back by any endpoint.
- **Avoiding a login-time fetch:** rather than a network round-trip on every login to learn onboarding status, `completeOnboarding` also best-effort syncs `app_metadata.onboarding_completed = true` via `supabase.auth.admin.updateUserById` (the admin-only `app_metadata`, not the client-editable `user_metadata`). `signInWithPassword`'s response always carries a freshly-minted token reflecting current DB state, so `login/page.tsx` reads `data.user.app_metadata.onboarding_completed` synchronously off that response, and the quiz page's own initial guard reads the same field off the locally cached session (`getSession()`, no network call) — both with zero extra requests. **`profiles.onboarding_completed_at` stays the single authoritative source** — the `app_metadata` copy is only ever a fast-path mirror, never read anywhere as ground truth.
- **Post-completion redirect explicitly refreshes the session — fixed bug.** `updateUserById`'s admin-API write updates `auth.users` in the DB, but it does **not** push a new JWT to the browser's already-issued session — `getSession()` keeps returning the pre-onboarding token, with `onboarding_completed` still absent from its `app_metadata` claim, until that token's next natural refresh (up to its full ~1hr TTL) or an explicit refresh. This was previously assumed to be harmless ("just an extra round-trip through the quiz page" — the outdated version of this note), but it isn't: `finishWith`'s `router.replace('/home')` would land on `/home`, whose `useRequireAuth` guard reads that same stale `getSession()` and immediately bounces back to `/onboarding/quiz` — which itself re-reads the identical stale session, sees onboarding still (apparently) incomplete, and just re-renders the quiz from step 1 with no indication anything succeeded. Net effect: any user who completes the quiz appears stuck on it and never reaches `/home`, confirmed via a script that watched navigation history past the first `/home` arrival (Playwright's `waitForURL('/home')` resolves on first match and doesn't catch the subsequent bounce, which is why this shipped unnoticed — `onboarding-quiz.spec.ts` now waits an extra beat and re-asserts the URL for exactly this reason). **Fix:** `finishWith` (`onboarding/quiz/page.tsx`) calls `supabase.auth.refreshSession()` — forcing GoTrue to mint a fresh token reflecting the just-written `app_metadata` — before redirecting, for both the success path and the `409 already_completed` path. Best-effort (swallowed on failure): worst case reverts to the old bounce-once behavior rather than blocking the redirect entirely.

## Environments

Two environments: local dev (Supabase CLI) and prod (Supabase cloud + Render).

**Local dev:** `supabase start` spins up a full Postgres + Auth + Studio stack in Docker. URLs and keys are printed on startup — copy them into `src/client/.env.local` and `src/server/.env.local`. These files are gitignored.

**Prod:** env vars live in the Render dashboard only, never in files. The prod Supabase project is linked once via `supabase link --project-ref <ref>`.

**Migration workflow:** see README.md "Database migrations" for the full command sequence.

**Data API grants:** newly created tables aren't auto-exposed to Data API roles by default (`config.toml`'s `auto_expose_new_tables`, off by default — matches the cloud default, and the flag itself is slated for removal). Without an explicit `GRANT`, even `service_role` gets "permission denied" on a brand-new table via `supabase-js`/PostgREST — confirmed against a live local instance. `20260630160450_grant_service_role_access.sql` grants `service_role` access on the schema as it stood at that point, plus `ALTER DEFAULT PRIVILEGES` so future tables inherit it automatically — any new table added via a later migration doesn't need its own grant.

**RPC function grants — the opposite default from tables, and it doesn't inherit the grant above:** Postgres grants `EXECUTE` on a newly created function to `PUBLIC` by default, and `config.toml` exposes the `public` schema over PostgREST — so an un-revoked `SECURITY DEFINER` function is callable by `anon`/`authenticated` via `/rest/v1/rpc/<fn>` with just the anon key, bypassing whatever app-layer checks the caller assumed protected it. `20260701142827_lock_down_session_rpcs.sql` revokes `EXECUTE` on `join_session_atomic`, `cancel_rsvp_and_promote`, and `decrement_reliability_score` (see "RSVP & attendance concurrency safety" below) from `PUBLIC`/`anon`/`authenticated` and grants it only to `service_role`. This is a per-function grant, not schema-level — any new `SECURITY DEFINER` RPC needs its own explicit revoke/grant pair, the `ALTER DEFAULT PRIVILEGES` trick above only covers tables/sequences.

**App deployment:** Render watches the repo and auto-deploys on push to `main`. No separate deploy step.

## Testing

**Unit suite (`npm test --workspace=server`):** every existing `*.service.test.ts`/`*.router.test.ts` mocks `lib/supabase.ts`'s `supabase.from()` entirely — fast, no Docker, verifies branching/row-mapping logic given an assumed DB response shape. Scoped via `vitest.config.ts`'s `include: ['src/**/__tests__/**/*.test.ts']`, so it never touches `src/__integration__/`.

**Integration suite (`npm run test:integration --workspace=server`, `src/server/src/__integration__/`):** runs the real `*.service.ts` code against a real local Postgres, for the specific class of bug mocks structurally can't catch — constraint violations, real PostgREST response shapes, untested migrations. Deliberately light: a couple of targeted tests, not a parallel copy of the unit suite. Requires `supabase start` (Docker) and `src/server/.env.local` populated from its printed output, same as `dev`. Separate `vitest.integration.config.ts` (`fileParallelism: false` — tests share DB state via truncate-between-tests cleanup, see below) so the default `npm test` stays Docker-free.

**Fixtures (`src/server/src/test/integration-helpers.ts`):** `profiles.id` references `auth.users(id)`, with a trigger auto-creating the `profiles` row on insert — so test users must go through `supabase.auth.admin.createUser(...)`, never a direct `profiles` insert. `createTestUser` wraps that plus an optional `profiles` patch (e.g. `placementSessionsRemaining: 0` to opt a fixture out of placement-mode scoring, matching the unit suite's baseline assumptions; or `firstName`/`lastName`/`verifiedTier` to build a verified-user fixture in one call for `profiles_verified_requires_name` CHECK constraint tests — see `user.integration.test.ts`).

**Frontend e2e (`npm run test:e2e --workspace=client`, `src/client/e2e/`):** Playwright, configured in `src/client/playwright.config.ts`. `webServer` auto-starts `next dev` against `http://localhost:3000` if nothing's already listening there (`reuseExistingServer: true` outside CI, so it won't collide with a dev server you already have running). Two projects run every spec: `chromium` (desktop) and `mobile-chromium` (`Pixel 7` viewport) — mirrors the mobile-first priority from "Platform" above. Only Chromium is installed locally (`npx playwright install chromium`); add Firefox/WebKit projects and run `npx playwright install` for those engines if cross-browser coverage becomes a requirement.

**Isolation — truncate via a direct `pg` connection, not transaction rollback:** PostgREST executes each HTTP request as its own transaction, so multi-call flows like `submitRating` (several sequential `supabase.from()` calls) can't be wrapped in one outer transaction without bypassing PostgREST — which would defeat testing through the real client. Instead, `afterEach` runs `TRUNCATE TABLE auth.users, venues CASCADE` over a raw `pg.Client` (used only for this, never by code under test): `CASCADE` follows the FK graph regardless of each FK's own `ON DELETE` action, reaching every dependent table without hand-maintaining a deletion order; `venues` is listed explicitly since unclaimed venues aren't reachable from `auth.users`. No `RESTART IDENTITY` — every table uses a uuid PK, and the local `postgres` role isn't a true superuser, so it can't reset sequences it doesn't own (e.g. auth's internal `refresh_tokens_id_seq`, which `CASCADE` would otherwise try to touch).

## Database Logic

**Venue availability lookup (two-step) — not yet implemented:** `venue.service.ts` currently returns raw `venue_hours` rows as-is (see `toVenue()`); nothing applies this lookup logic, and `venue_date_exceptions` isn't read or written anywhere in code yet (the table exists in the migration, unused). The intended logic, once built:
1. Check `venue_date_exceptions` for the exact date. If a row exists: null `open_time` means fully closed; non-null times override the regular schedule.
2. If no exception row, fall back to `venue_hours` for that `day_of_week`.

**Venue hours granularity:** `venue_hours` uses day-of-week only. "1st and 3rd Tuesday" patterns are out of scope for v1 — `venue_date_exceptions` handles one-offs, and weekly schedules cover the vast majority of real venues at launch.

**Write access for `venue_date_exceptions` (not yet implemented — no endpoint exists):** intended to be claimed venue accounts (those with `claimed_by_account_id` set) only. For unclaimed venues, platform admins only.

**Rating display derivation:** see "Rating System" above for the full formula, clamping, and label format (`toRatingDisplay` in `rating.service.ts`). Always computed server-side from `internal_score` — never expose the raw float to the client.

**Admin access check:** not an RLS policy (none exist in this schema — see "Row Level Security" above). Enforced in service-layer code via `isAdmin()` (`venue.service.ts`): a plain `select user_id from admins where user_id = :userId`. Follow this pattern — a service-layer query, not a DB policy — for any new admin-gated write.

**Claim-style writes (race-safe):** a "claim" or other check-then-act write should be a single atomic `UPDATE ... WHERE <precondition>` rather than a separate `SELECT` followed by an unconditional `UPDATE` — see `venue.service.ts`'s `claimVenue` (`.eq('id', id).is('claimed_by_account_id', null)`) and `updateVenue` (non-admins get `.eq('claimed_by_account_id', userId)` folded into the same `UPDATE`). A 0-row result (`.single()` errors) means the precondition failed at write time, including races against other concurrent writers — the precondition can't go stale between a separate check and the write the way it could with two queries. Follow this pattern for any new claim/ownership-gated write.

**User profile fields not yet exposed:** `getUserById`/`updateUser` (`user.service.ts`) only select and return the `User` shape. `profiles.reliability_score`/`session_count` exist in the schema (see database-schema.md) but aren't selected or returned by either function. `UserProfile` (in `@pavilion/types`, extends `User` with `rating`, `reliabilityScore`, `sessionCount`) is declared but no service function builds one yet — there's no endpoint that returns it. Add a dedicated `getUserProfile()`-style function (selecting the extra columns plus the rating display) if/when this needs to go live, rather than adding the fields to `getUserById`.

**Verification approval action:** on approving a `verification_requests` row, write `verified_tier` and `rating_floor` to the corresponding `profiles` row. `rating_floor` is set to 6.0 regardless of the tier granted (pro floor per product rules). `first_name`/`last_name` are nullable and optional for unverified users but required once `verified_tier` is set — enforced by the `profiles_verified_requires_name` CHECK constraint (`supabase/migrations/20260701160000_add_user_first_last_name.sql`), not app-layer validation, so this holds regardless of how `verified_tier` gets written (including the direct-DB-access path noted in the scope note above). When the approve/reject flow is built, it should reject approval up front (with a clear error) if the requester's name fields are empty, rather than letting the write fail on the DB constraint. After approval, the name becomes immutable through `PATCH /api/users/:id` — see "Client Application Shell" → "Verified users' names are locked" above.

**Waitlist ordering:** determined by `session_rsvps.joined_at` ascending. When a `'going'` RSVP is cancelled, promote the oldest `'waitlisted'` row for that session.

**RSVP & attendance concurrency safety — implemented as Postgres functions, called via `supabase.rpc(...)` from `session.service.ts`** (`supabase/migrations/20260701000000_atomic_score_decrement.sql`, `20260701000001_atomic_rsvp_operations.sql`, `20260701150000_skip_promotion_on_dead_sessions.sql`): naive read-then-write JS for capacity checks, waitlist promotion, and reliability-score deductions is racy under concurrent requests — overbooking past `max_players`, double-promoting the same waitlisted user, or double-applying a penalty. Fixed by moving each check-and-write into a single-transaction SQL function instead:
- `join_session_atomic(session_id, user_id)` locks the `sessions` row (`FOR UPDATE`), counts `going` RSVPs, and inserts/upserts the RSVP with the resulting status in one transaction — two concurrent joins for the last slot are serialized by the row lock, not by JS.
- `cancel_rsvp_and_promote(session_id, user_id)` takes the same `FOR UPDATE` lock on `sessions`, so all concurrent cancellations for a session serialize through it, then cancels the RSVP and promotes the oldest `'waitlisted'` row in the same transaction — but only when the session's `status` is `'upcoming'` or `'active'`; cancelling on a `'cancelled'`/`'completed'` session still cancels the RSVP but skips promotion, since promoting someone onto a dead session would create a phantom RSVP that could later earn a no-show penalty. Deliberately avoids `SELECT ... FOR UPDATE SKIP LOCKED` on the waitlist row — if the transaction holding that lock had rolled back, `SKIP LOCKED` would already have promoted a lower-priority user, permanently breaking FIFO order.
- `decrement_reliability_score(uids, points)` applies `GREATEST(0, reliability_score - points)` in a single `UPDATE`, avoiding a read-then-write race between overlapping late-cancel/no-show penalties for the same profile.

All three are `SECURITY DEFINER` and locked down to `service_role` only — see "RPC function grants" under Environments above. App-layer authorization (ownership, skill gating) still lives entirely in `session.service.ts`; these functions only make the capacity/promotion/decrement step atomic, they don't re-check who's allowed to call them.

`markAttendance` (`session.service.ts`) has its own, JS-level version of this problem: the read of `going` RSVPs used to decide who attended/no-showed and the writes that flip their status aren't one atomic unit, so two overlapping calls (e.g. a client retry) could both read the same snapshot and both fire the no-show penalty for the same user. Fixed without a new RPC — both the attended-update and no-show-update queries add `.eq('status', 'going')` and `.select('user_id')`, so each call only sees the rows *it* actually flipped; the reliability-score RPC and the `{ attended, noShows }` counts are computed from that returned set, not the earlier read, so a call whose UPDATE affects zero rows (because a concurrent call already flipped them) naturally skips the penalty instead of double-deducting it.

`cancelRsvp`'s late-cancel penalty RPC is best-effort once the cancel itself has committed: if `decrement_reliability_score` errors after `cancel_rsvp_and_promote` already succeeded, the function logs the error and returns `{ ok: true, warning: 'penalty_not_applied' }` rather than reporting the cancel as failed — the RSVP really is cancelled at that point, so `{ ok: false }` would be a lie. `markAttendance`'s no-show branch instead returns `{ ok: false, reason: 'write_failed' }` on the same RPC error, since nothing there has an equivalent "already committed, can't take it back" constraint.

Verified against a real concurrent race (not just mocked RPC calls) in `src/server/src/__integration__/session.integration.test.ts` — see Testing above.

## Session & Venue

**`venues.lng`/`lat` are stored, unlike other derived values — and that's fine:** the broader rule (see CLAUDE.md) is that *business-logic* derivations (rating tier, shuttle cost) are computed server-side on every read, never cached, to avoid staleness. `lng`/`lat` are a different thing: `STORED GENERATED` columns that Postgres keeps in lockstep with `location` on every write — they can't drift, and exist only to dodge a wire-format problem (PostgREST returns `geography` as an EWKB hex string, not `{ coordinates: [...] }`), not to cache a business rule. Don't read this as license to start storing other derived values.

**Session domain — implemented in `src/server/src/domains/session/`:**
- `session.service.ts` + `session.router.ts`, with unit tests in `__tests__/`
- `organizer_id` is always required — even drop-in sessions need a poster (the person who creates it). Venue-owned standing sessions can be created by admins with their own `organizer_id`. Revisit when the venue-account flow is built.
- Recurring sessions: `is_recurring` and `recurring_cron_expr` are stored on create; child-session auto-spawning is deferred (no cron job yet).
- `profiles.session_count` is not incremented by the RSVP flow — it requires a separate post-session reconciliation process (not yet built).
- No-show *marking* is manual: the organizer calls `POST /:id/attendance` after the session completes (see API table). Automatic no-show detection (without organizer input) is a separate background-process concern, not yet built.

**Payment model (v1): no in-app payments**
- Platform is coordination-only. Organizers collect payment externally (cash, Venmo, etc.).
- No-show enforcement is social: late cancellations and no-shows affect the reliability score. Enough strikes = blocked from paid sessions.
- 12-hour cancellation window measured from session start time: cancelling within 12 hours of `starts_at` deducts 5 points from `profiles.reliability_score` (clamped to 0).
- No-show penalty: deducts 10 points from `profiles.reliability_score` (clamped to 0) when the organizer marks a `going` attendee as absent via `POST /:id/attendance`.
- Waitlist fills dropped spots automatically (oldest `'waitlisted'` RSVP by `joined_at` is promoted to `'going'` when a `'going'` RSVP is cancelled).

In-app payments (Stripe Connect) and shuttle cost auto-calculation are both deferred — see brainstorm.md's Future Features Roadmap for the design detail.

**Skill range enforcement (asymmetric) — implemented in `session.service.ts` (`joinSession`):**
- Session range stored as `[skill_min, skill_max]` in decimal (`numeric(4,2)` columns — see database-schema.md)
- **Input validation (`session.router.ts`'s `validateSessionFieldValues`, shared by `POST /` and `PATCH /:id`):** `skillMin`/`skillMax` must be numbers within `[MIN_SKILL, MAX_SKILL]` = `[1, 99.99]` — `MAX_SKILL` is the `numeric(4,2)` column's actual ceiling (a 3+ digit integer part like `123` overflows Postgres's numeric type), not a product-chosen number, so this can never reject a legitimately high (e.g. verified pro-tier) range while still catching the crash case. Same function also validates `courtCount`/`maxPlayers`/`durationMinutes` (positive), `shuttleTubePrice` (`0`–`9999.99`, matching its own `numeric(6,2)` column), and the enum fields, closing what was previously a validation gap unique to `PATCH /:id` (it had none at all, unlike `POST /` and unlike `user.router.ts`'s `PATCH`). `updateSession` (`session.service.ts`) additionally cross-checks a partial `skillMin`-or-`skillMax`-only patch against the session's current stored counterpart (a pre-update `SELECT`) so a single-field patch can't invert the range invisibly — returns `{ ok: false, reason: 'invalid_skill_range' }`, surfaced as `400`.
- **Organizer range warning (on create):** if the organizer's `floor(internal_score)` is >1.5 grades from both `skill_min` and `skill_max`, `createSession` succeeds but returns `warning: 'skill_range_wide'`. Not a block — organizers can host sessions outside their exact grade (e.g., an advanced player hosting a beginner drop-in).
- **Player join check (`joinSession`):**
  - Playing up (`skill_min - player_score > 1.5`): hard block (`skill_blocked`)
  - Playing up (0 < `skill_min - player_score` ≤ 1.5): allowed with `warning: 'playing_up'`
  - Playing down (`player_score - skill_max > 3.0`): hard block (`skill_blocked`)
  - Playing down (0 < `player_score - skill_max` ≤ 3.0): allowed with `warning: 'playing_down'`
  - Organizer joining their own session: skill check skipped entirely
- **Not yet implemented:** organizer notification when a high-rated player joins; `strict_range` toggle (column exists, not enforced); rating dampening for out-of-range players (rating domain's responsibility — threshold TBD ~1.5 grades above ceiling)

## Messaging

- **v1 scope:** session-scoped group chat only (organizer + attendees). No open DMs in v1.
- **Recommended provider: Stream Chat** — pre-built React components, generous free tier, scales well. Integration measured in days not weeks. Handles real-time, push notifications, message storage, and moderation primitives.
- Alternatives: Firebase Realtime Database (more custom UI work, very cheap), Sendbird (more enterprise, pricier)
- **Channel ID convention:** Stream channel IDs are derived as `session_{session_id}`. No `stream_channel_id` column on `sessions` — the ID is always reconstructible from the session UUID, so there's nothing to store or sync.
- DM system is a future feature — keep the messaging domain cleanly separated from session domain so it can be extended
